## 1. 保険基盤システム AWS 移行プロジェクト (現在参画中) {#proj1}

### プロジェクト概要

AWS上に構築されたデータ蓄積・分析システムにおいて、経営統合に伴うセキュリティ是正プロジェクトへ参画。  
Security Hubで検出されたセキュリティ項目について、顧客折衝から設計・実装・本番反映まで一貫して担当。

### チーム体制

- 運用チーム：3名
- ETL対応：2名
- セキュリティ是正対応：1名

### ① セキュリティ是正

#### 概要

Security Hubで検出された各種セキュリティ設定について、AWSサービスごとに是正対応を実施。

#### 背景・課題

経営統合に伴い、AWS環境全体でセキュリティポリシーを統一する必要があった。  
Security Hubでは多数の検知項目が存在していたため、全てを是正するのではなく、業務影響や必要性を考慮した判断が求められた。

#### 担当内容

- 対象リソース調査
- 顧客との是正方針調整
- 開発環境テスト
- 実装修正
- 本番反映
- 検証

#### 検討・判断したこと

AWSベストプラクティスだけではなく、運用影響も考慮して是正可否を整理。  
是正不要と判断した、または作業工数を削減した項目については理由を整理した上で顧客へ提案した。

- Athenaのクエリ結果を暗号化する対応においてAthena設定からの暗号化をする想定だったが、クエリ結果を格納しているS3バケットが既にデフォルトで暗号化されているため顧客へ提案し是正不要で整理
  - AWSの推奨設定だけを適用するのではなく、既存構成や運用状況を確認した。
  - クエリ結果保存先S3バケットで既に暗号化が有効となっており、実運用上リスクが低いと判断。
  - その根拠を整理し、顧客へ是正不要として提案した。
- 共通管理アカウントでVPCエンドポイントを集約しており、各ワークロードアカウントから接続可能な構成だったため、重複作成を避ける提案を行った

### 成果

- 不要な是正作業を削減
- セキュリティ強化
- 工数削減

### 使用技術

- Security Hub
  - セキュリティ検知

- IAM
  - アクセス制御見直し

- KMS
  - 暗号化設定

- S3
  - Bucket Policy
  - 暗号化設定

- CloudTrail
  - 監査ログ

- GuardDuty
  - マルウェア検知

### ② コスト影響調査

#### 概要

Security Hub是正によるAWS利用料金への影響を調査。

#### 背景・課題

GuardDuty等では設定変更に伴い追加料金が発生する可能性があった。

#### 担当内容

- Cost Explorer調査
- AWS料金試算
- 顧客説明

#### 検討・判断したこと

月間利用量を基に概算コストを算出し、導入可否判断材料を提示した。

- GuardDuty Malware Protection for S3において、バケット数が300超えになってしまい運用が現実的ではないことを顧客に提案し、データを集約している重要なバケットのみ指定しコストを削減。
- 使用されず残置されているVPCやSGなどの通信系のリソースを割り出し、削除することで約$15のコスト削減を実現。

### プロジェクト成果

- AWS全体のセキュリティ強化
- 不要是正を整理し工数削減
- 運用ルール整備

## 2. 保険基盤システム AWS 移行プロジェクト {#proj2}

### プロジェクト概要

AIX環境で稼働していた保険基盤システムをAWSへ移行するプロジェクトに参画。
インフラ担当としてコンテナ実行基盤の設計・構築からCI/CD環境の整備まで担当した。

### チーム体制

- インフラ：7名
- アプリ：18名
- テスト：11名

### ① コンテナ実行基盤（ECS / ECR）

#### 概要

Javaアプリケーションをコンテナ化し、
AWS ECS上で稼働する実行基盤を構築した。

#### 背景・課題

AIX環境ではアプリケーションを直接デプロイしており、環境ごとの差異が発生しやすく、デプロイ作業も手順に依存していた。  
また、DEV・QA・Prod・DRの4環境それぞれで設定差異が生じやすく、運用負荷が高い状況だった。

#### 担当内容

- ECS Cluster設計
- Task Definition設計
- Service設計
- Health Check設計
- ECR Repository作成
- 各環境へのデプロイ

#### 検討・判断したこと

- 4環境で同一構成を採用することで構築品質と再現性を高める方針とした。
  - 各環境でTask Definitionを個別管理していた場合、修正漏れや設定差異が発生しやすく、保守性にも課題があると考えた。
  - そのためTask Definitionに定義する環境変数やリソース設定のみで環境差異を吸収し、コンテナイメージは共通利用できる構成へ見直した。
  - これにより、環境ごとの修正漏れを防止するとともに、保守工数を削減した。
  - 不要な設定変更を回避することで、環境間の構成差異を抑え、運用品質の向上につなげた。
- Jenkins パイプラインを環境ごとに管理すると修正漏れやレビュー負荷が増えるため、パイプライン自体は共通化し、環境変数で切り替える構成とした。

#### 成果

- 4環境を標準化
- 構築品質向上
- 運用性向上

#### 使用技術

AWS ECS

- Cluster設計
- Service設計
- Task Definition設計
- Health Check設定

AWS ECR

- コンテナイメージ管理

Docker

- Javaアプリケーションのコンテナ化

### ② 共有ストレージ（EFS）

#### 概要

コンテナ間で共有するログ保存領域としてEFSを構築。

#### 背景・課題

コンテナはライフサイクルが短く、ローカルストレージへ保存したログは永続的に保持できないため、共有ストレージが必要だった。

#### 担当内容

- EFS構築
- マウント設定
- アクセス権設定

#### 検討・判断したこと

複数コンテナからアクセスできる共有ストレージとしてEFSを採用。  
ログを永続化することで障害解析しやすい構成とした。

#### 使用技術

- AWS EFS
  - 共有ストレージ構築

### ③ JenkinsによるCI/CD

#### 概要

デプロイ作業を自動化するCI/CD環境を構築。

#### 背景・課題

元々エンドユーザーではJenkinsを活用されていたが、各環境ごとにJenkinsパイプラインが用意されていた。  
それにより、環境の指定ミスによるデプロイ失敗の増加が課題となっていた。

#### 担当内容

- Jenkins パイプライン改修

#### 検討・判断したこと

全環境共通のJenkinsパイプラインを用意することにより、環境変数などを用いてすべての環境で使用できるよう整備した。

#### 成果

- デプロイ時間を平均15分→5分へ短縮
- 環境ごとのパイプライン管理を廃止し、保守性を向上

#### 使用技術

- Jenkins
- GitHub
- AWS CLI
- ECS
- ECR

### プロジェクト成果

- Task Definitionを共通化し、4環境の設定差異を削減
- 環境差異をTask Definitionへ集約し、保守性を向上
- デプロイ時間30分→10分へ短縮
- クラウド移行を支援
- 構築手順書を整備し再現性を向上

### ② Ansible自動化

#### 概要

#### 背景・課題

#### 成果

作業時間30%削減

### ③ RHEL9対応

#### 概要

OS更改に伴うAnsibleエラー調査。

#### 背景・課題

- RHEL9ではOS仕様変更によりPlaybookエラーが多数発生した。
- 過去対応でRHEL9の対応実績はあったのだが、ナレッジとして残っていなかった。

#### 担当内容

- 差分調査
- 原因分析
- Playbook修正
- ナレッジ展開

#### 検討・判断したこと

RHEL9ではOS仕様変更によりAnsibleエラーが多発した。  
原因を調査した結果、

- network.service廃止
- yum→dnf
- systemd差異

などOS仕様差分が原因と判断。  
同様の問題が他スクラムでも発生する可能性があると考え、Playbook修正だけで終わらせず、OS差分をナレッジ化し、全スクラムへ共有した。  
ナレッジ化したことで、他スクラムでも同様の問題を迅速に解決できるようになった。

#### 成果

- 他チーム40時間削減
- 調査時間50%短縮

### プロジェクト成果

- AWS基盤構築
- Ansible自動化
- RHEL9対応標準化
- IAM運用品質向上
